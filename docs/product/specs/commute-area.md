# 생활권 탐색 기능 명세

- 상태: 검토용 초안 v0.1 / 작성일: 2026-10-09 / 대상: 스프린트 2

## 1. 목적과 범위

사용자는 회사·학교 같은 목적지를 입력해, 대중교통으로 제한 시간 안에 출퇴근할 수 있는 동네를 찾는다.

자취선배의 기존 기능은 매물을 정한 뒤의 임장 단계에 집중되어 있다. 이 기능은 그보다 앞 단계인 "어디에 살지 정하는 단계"를 맡아 서비스의 진입점을 넓힌다.

### 1.1. 기능 선정 기준

| 기준 | 이 기능이 만족하는 방식 |
| --- | --- |
| 사용자에게 매력적이어야 한다 | 매물을 먼저 고르고 거리를 따지는 기존 방식과 달리, 통근 시간에서 출발해 동네 후보를 좁힌다. 지역을 잘 모르는 상경 사용자도 어느 동네부터 알아볼지 바로 알 수 있다. |
| 자체 데이터셋 없이 가치를 만들 수 있어야 한다 | KTDB(국가교통DB) 대중교통 GTFS와 행정동 경계 같은 공개 데이터만으로 동작해, 첫 사용자부터 같은 품질의 결과를 준다. |

### 1.2. 범위

| 구분 | 내용 |
| --- | --- |
| 이번 범위 | GTFS 노선망 적재, 목적지 기준 도달권 탐색, 행정동 단위 결과 표시 |
| 후속 범위 | 정류장별 상세 경로 안내, 실거래 월세 정보와의 통합, TAGO 실시간 정보 연동 |
| 제외 | 자가용·도보 전용 통근, 매물 단위 추천 |

## 2. 요구사항

- `REQ-COMMUTE-001`: 목적지를 주소 검색 또는 지도 선택으로 지정한다.
- `REQ-COMMUTE-002`: 최대 통근 시간을 선택한다.
- `REQ-COMMUTE-003`: 목적지까지 최대 통근 시간 안에 도착할 수 있는 동네를 행정동 단위로, 통근 시간과 함께 확인한다.
- `REQ-COMMUTE-004`: 결과 동네를 선택해 지도에서 위치를 확인한다.
- `REQ-COMMUTE-005`: 운영자는 GTFS 파일로 대중교통 노선망을 적재·교체한다.

## 3. 정책

### 3.1. 통근 시간 계산

- `POL-COMMUTE-001`: 통근 수단은 버스와 지하철·도시철도다. GTFS `route_type`이 `0`, `1`, `3`인 노선만 사용하고, KTDB 데이터에서 버스에 쓰는 `0`도 포함한다. 일반철도·항공·해운은 제외한다.
- `POL-COMMUTE-002`: 정류장 간 이동 시간은 같은 구간을 지나는 운행편 이동 시간의 중앙값으로 한다. 같은 분에 도착하는 구간도 최소 30초로 본다.
- `POL-COMMUTE-003`: 노선에 탑승할 때마다 대기 시간을 더한다. 대기 시간은 첫 정류장 출발 간격 중앙값의 절반이며, 2분 이상 15분 이하로 제한한다. 쓸 수 있는 간격이 없으면 5분으로 둔다.
- `POL-COMMUTE-004`: 정류장 간 도보 환승은 GTFS `transfers.txt`의 최소 환승 시간을 쓴다. 같은 정류장 쌍이 여러 번 나오면 가장 짧은 시간을 쓴다.

### 3.2. 데이터

- `POL-COMMUTE-005`: 노선망 원천은 KTDB 대중교통 GTFS 2025년 3월 데이터셋이다. 노선 26,399개, 정류장 215,409개, 정차 기록 18,889,140건이다.
- `POL-COMMUTE-006`: 적재는 기존 노선망을 모두 지우고 새로 채우는 전체 교체다. 파일을 모두 읽은 뒤 삭제와 저장을 한 트랜잭션으로 처리해, 실패하면 이전 노선망을 유지한다.
- `POL-COMMUTE-007`: 대상 노선이 실제로 지나지 않는 정류장과, 양쪽 정류장이 모두 적재 대상이 아닌 환승은 적재하지 않는다.

## 4. 인수 기준

| ID | 조건과 행동 | 관찰할 결과 |
| --- | --- | --- |
| AC-COMMUTE-001 | `GTFS_DIRECTORY`에 GTFS 파일 5개를 두고 적재 API를 호출한다. | 노선·정류장·구간·환승 건수가 응답되고 `gtfs_*` 테이블이 그 건수로 채워진다. |
| AC-COMMUTE-002 | 적재된 상태에서 다른 GTFS로 다시 적재한다. | 이전 노선망은 남지 않고 새 노선망만 조회된다. |
| AC-COMMUTE-003 | `GTFS_DIRECTORY`가 비어 있거나 파일이 없는 상태로 적재 API를 호출한다. | 적재가 실패하고 기존 노선망은 그대로 남는다. |
| AC-COMMUTE-004 | 목적지와 최대 통근 시간을 지정해 탐색한다. | 최대 통근 시간 안의 동네만 행정동 단위로 통근 시간과 함께 표시된다. |
| AC-COMMUTE-005 | 최대 통근 시간을 늘려 같은 목적지로 다시 탐색한다. | 이전 결과의 동네가 모두 포함되고 동네 수는 같거나 늘어난다. |

## 5. 가설 검증

사용자 인터뷰로 기능의 매력과 전제 문제를 검증한다. 매력은 끌림 → 발견 → 몰입의 세 단계로 보고, 핵심인 **발견**은 체험 전후의 후보 동네 목록을 비교해 숫자로 판정한다.

### 5.1. 대상과 진행

대상은 최근 1~2년 안에 처음 자취를 시작했거나 3개월 안에 시작할 사람 중, 목적지 지역을 잘 모르는 사람 5~8명이다. 참여자 한 명당 약 25분 진행한다.

1. **과거 경험 (10분)**: 기능은 아직 보여 주지 않는다.
    - 동네는 어떻게 정했나요? 첫 후보는 어디서 나왔나요?
    - 통근 시간은 어떻게, 몇 번 확인했나요?
    - 가장 막막했던 순간은 언제였나요?
2. **체험 전 목록**: "지금 회사 기준으로 알아볼 동네를 모두 적어 주세요."
3. **기능 체험 (10분)**: "회사(학교)를 넣고 살 만한 동네를 골라 보세요." 설명 없이 관찰만 한다.
4. **체험 후 목록**: "알아볼 동네를 다시 적어 주세요."
5. **마무리 (5분)**: "이 결과로 동네를 정할 수 있나요? 더 알아야 할 게 있다면 무엇인가요?"

### 5.2. 참여자별 기록

| 항목 | 결과 | 근거 (발언·행동) |
| --- | --- | --- |
| 체험 전 후보 동네 |  |  |
| 체험 후 후보 동네 |  |  |
| **발견**: 새로 추가된 동네 수 (통근 기준 충족) |  |  |
| 끌림: 설명 전에 스스로 목적지를 입력했다 | 나타남 / 애매 / 안 나타남 |  |
| 몰입: 조건을 바꿔 2번 이상 다시 검색했다 | 나타남 / 애매 / 안 나타남 |  |
| 문제: 동네 정하기가 막막했다고 스스로 말했다 | 나타남 / 애매 / 안 나타남 |  |
| 기존 방식: 매물마다 통근 시간을 따로 확인했다 | 나타남 / 애매 / 안 나타남 |  |
| 가격 수요: 스스로 가격을 물었거나 마무리에서 먼저 꼽았다 | 나타남 / 애매 / 안 나타남 |  |

### 5.3. 판정 기준

- 새로 추가된 동네가 1개 이상이면 그 참여자는 발견으로 본다.
- 전체의 절반 이상이 발견이면 기능이 매력 있다고 판단한다.
- 가격 수요가 절반 이상에서 나타나면 실거래 월세 기능과의 통합 근거로 쓴다.
- 기준은 인터뷰 전에 팀이 합의하고, 결과를 본 뒤 바꾸지 않는다.

### 5.4. 진행 시 주의

- 의견("쓰실 건가요?") 대신 겪은 일("어떻게 했나요?")을 묻는다.
- 체험 중에는 안내하지 않는다. 막히면 "지금 무엇을 찾고 계세요?"만 묻는다.
- 기록자 두 명이 따로 체크하고, 결과가 다르면 녹음을 다시 들어 합의한다.

## 6. 미정 사항과 결정 근거

- 로그인 없이 탐색할 수 있게 할지 정해야 한다. 진입 장벽을 낮추는 데 중요하므로 게스트 정책과 함께 결정한다.
- 최대 통근 시간의 선택지와 기본값, 최대 환승 횟수, 도보 속도는 아직 정하지 않았다.
- 행정동의 대표 통근 시간을 동 안 정류장 중 가장 짧은 시간으로 할지 정해야 한다.
- 실거래 월세 정보와 통합할지는 가설 검증의 가격 수요 결과로 결정한다.
- GTFS 적재 API는 로그인한 회원이면 누구나 호출할 수 있다. 관리자 권한을 둘지 정해야 한다.
- 탐색 API는 요청마다 전국 노선망을 읽으면 병목이 될 것으로 예상한다. 부하 테스트로 병목을 확인한 뒤 메모리 적재, 결과 캐시, 동시 실행 제한 순으로 개선한다.
