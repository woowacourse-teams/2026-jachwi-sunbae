# 안드로이드 앱 웹뷰 정기 측정

PR마다 도는 화면 판정(`Check visual verdict`)은 데스크탑 Chromium에 보통 4G와 CPU 4배 제한을 건 흉내 값이다. 실제 앱은 같은 웹을 React Native WebView로 감싸고, 실사용 데이터에서는 Android 웹뷰가 가장 느렸다. 이 문서는 주 1회 안드로이드 에뮬레이터의 앱 웹뷰에서 사용자 흐름을 재고, 이력과 견줘 이상을 판정하고, 확인된 문제만 팀 이슈로 올리기까지의 흐름과 운영 설정을 적는다.

- 워크플로: [android-webview-calibration.yml](../../.github/workflows/android-webview-calibration.yml)
- 스크립트: [.claude/skills/verify-jachwi/scripts](../../.claude/skills/verify-jachwi/scripts)의 `measure-android.mjs`, `android-scenarios.mjs`, `calibration-history.mjs`, `calibration-judge.mjs`, `perf-issue.mjs`
- 셸 앱과 에뮬레이터 스크립트: [.claude/skills/verify-jachwi/android](../../.claude/skills/verify-jachwi/android)
- 흉내 측정과 PR 판정: [verify-jachwi 스킬](../../.claude/skills/verify-jachwi/SKILL.md)

## 흐름 한눈에

| 시각과 주체                              | 하는 일                                                                                                            | 남는 것                                                       |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |

schedule은 기본 브랜치(develop)의 워크플로 파일로 돌고, cron은 `0 15 * * 0`(UTC 일요일 15:00, 한국 월요일 0:00)이다. 에뮬레이터를 띄워 20분쯤 걸려 PR마다는 돌리지 않는다.

## 측정 환경

- ubuntu 러너에서 `reactivecircus/android-emulator-runner`(KVM, API 35 google_apis x86_64, pixel_6, swiftshader)로 에뮬레이터를 띄운다. 이미지의 WebView와 크롬은 124다.
- 같은 운영 빌드를 `serve.mjs --api mock --delay 300 --cache prod --faults`로 띄운다. 모든 `/api` 응답은 300ms 뒤에 오고, 정적 파일은 운영(`publish.sh`)과 같은 캐시 헤더를 쓴다. `--faults`는 실패 주입을 켠다.
- 목 시나리오의 네이버 지도 SDK는 무게만 같은 목(`map-sdk-stub.mjs`)이다. 지도는 뜨지 않으므로 지도를 눌러야 하는 단계는 실제 지도 시나리오에서만 잰다(아래 "실제 지도와 실사용 값").
- 회선은 CDP로 보통 4G(지연 70ms, 내려받기 9Mbps)를 걸고, CPU는 기기 그대로다.
- 앱 웹뷰는 `mobile/App.tsx`의 WebView 설정(UA 꼬리 `JachwiSunbae/<버전> android`, DOM 저장소, 혼합 콘텐츠 차단, 서드파티 쿠키 끔, 위치 허용)을 옮긴 최소 셸 앱(`android/webview-shell`)이다. 네이티브 맥락 스크립트는 `mobile/src/webBridge.ts`를 그대로 넣는다.

## 시나리오

정의는 `android-scenarios.mjs`의 `SCENARIOS` 한 곳이다. 흐름이나 재는 순간을 바꾸면 `version`을 올린다. 각 시나리오는 5회 재고, 앞에 세지 않는 데우기가 1회 있다.

| 이름         | 흐름                                                                                                               | 판정 값                                            | 함께 남기는 단계                                  |
| ------------ | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------- | ------------------------------------------------- |
| `cold`       | 앱 데이터를 지우고 목록 보기(`/?view=list`)를 연다                                                                 | 첫 목록 카드가 보인 시각                           | 목록 요청 시작, 응답 도착, 카드 표시, 받은 바이트 |
| `warm`       | `cold` 바로 뒤 앱만 껐다 켜서 같은 캐시로 다시 연다                                                                | 첫 목록 카드가 보인 시각                           | 위와 같음. 받은 바이트로 캐시가 먹는지 본다       |
| `register`   | 홈(지도 보기)에서 "현재 위치로 이동", 등록 제안의 "추가"를 누른다                                                  | "추가"부터 새 방 항목이 보이기까지                 | 저장 요청 시작, 저장 응답 도착, 새 방 항목 표시   |
| `geo-slow`   | `register`와 같되 페이지의 위치 응답을 3초 늦춘다                                                                  | "현재 위치로 이동"부터 새 방 항목까지              | 등록 제안 표시, 저장 응답 도착, 새 방 항목 표시   |
| `denied`     | 위치 권한 없이 "현재 위치로 이동"을 눌러 거부 알림을 보고, 주소 검색으로 위치를 고른 뒤, 권한을 켜고 다시 등록한다 | 권한을 켠 뒤 "현재 위치로 이동"부터 새 방 항목까지 | 거부 알림, 주소 검색 선택, 권한을 켠 뒤 등록      |
| `fail-reset` | 저장 요청 한 번을 500으로 만들고 "추가"를 누른다. 실패 알림 뒤 목 목록이 그대로인지 보고, 다시 눌러 등록한다       | "추가"부터 실패 알림까지                           | 실패 알림, 다시 등록해 새 방 항목 표시            |

- 등록하는 시나리오는 시작 전에 처음에 없던 방을 목 API로 지우고(DELETE), 목록 수가 처음과 같은지 확인한다. 회차마다 상태가 처음으로 돌아간다.
- `denied`에서 주소 검색으로 고른 자리에 바로 등록하려면 지도를 눌러야 한다. 지도 SDK 목에서는 지도가 뜨지 않아 그 단계는 재지 않고, 기록에 `selectionRegister`로 남긴다. 등록은 사용자가 설정에서 권한을 켜는 길(`pm grant`)로 한다.
- `geo-slow`의 지연은 페이지의 `navigator.geolocation.getCurrentPosition`을 늦춰 만든다. 앱의 위치 요청 제한(8초, 15초)보다 짧다.

### 실기기 권한 대화상자와 셸 검증의 차이

- 실제 앱(react-native-webview)은 앱에 위치 권한이 없으면 OS 권한 대화상자를 띄우고, 사용자가 고른 값으로 웹의 위치 요청에 답한다.
- 셸 앱은 대화상자를 띄우지 않는다. 웹의 위치 요청이 오면 그 순간 앱 권한(`checkSelfPermission`)을 보고 바로 답한다. 측정 스크립트가 `pm grant`와 `pm revoke`로 허용과 거부를 정한다.
- 그래서 셸의 `denied`는 "대화상자에서 거부를 누른 뒤"와 같은 상태만 재현한다. 대화상자가 뜨는 시간, 대화상자 문구, "다시 묻지 않음" 같은 실기기 동작은 셸 측정에 들어 있지 않고, 실기기에서 따로 확인한다.

### 실제 지도 시나리오

secret `NAVER_MAP_CLIENT_ID`가 있는 주 1회와 수동 실행에서만 돈다. 실제 키로 따로 빌드해 `localhost:3000`으로 띄우고, 지도 SDK 주소를 돌리지 않는다. 지도 SDK와 타일을 받는 시간이 우리 코드와 무관하게 흔들려 참고 값으로만 쌓고 판정과 이슈 후보에서 뺀다. 목 시나리오와 이름이 달라 이력이 섞이지 않는다.

| 이름               | 흐름                                                                                                           | 판정 값(참고)                                | 함께 남기는 단계                                            |
| ------------------ | -------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | ----------------------------------------------------------- |
| `real-map-overlay` | 앱 데이터를 지우고 홈(지도 보기)을 연다                                                                        | 우리 오버레이(마커, 경계)가 지도에 붙은 시각 | 지도 SDK 준비, 지도 만들어짐, 오버레이                      |
| `real-denied-pick` | 위치 거부 알림을 보고, 주소 검색으로 고른 뒤 지도 가운데(검색 핀 바로 아래)를 눌러 "본 방 기록하기"로 등록한다 | 지도를 누른 때부터 새 방 항목까지            | 거부 알림, 주소 검색 선택, 좌표 메뉴, 저장 응답, 새 방 항목 |

지도 인증이 실패하면 화면에 "지도를 연결할 수 없어요"가 뜨고, 그 회차는 환경 오류로 남는다.

## 이력과 비교

`calibration-history.mjs`가 실행마다 한 줄을 `history.jsonl`에 더하고 장기 요약 `SUMMARY.md`를 다시 만든다.

- 한 줄에 남는 것: 대상 커밋, 실행 링크, 환경(웹뷰와 Android 버전, 에뮬레이터, 회선, 목 지연), 시나리오별 버전, 성공 회수, 환경 오류와 앱 오류 회수, 중앙값, 범위, 단계별 중앙값, 받은 바이트, 다시 잰 결과.
- 비교: 이번 실행을 직전 실행, 최근 4회(이번 커밋을 뺀 같은 조건, 성공 3회 이상, 커밋마다 가장 최근 하나)의 중앙값과 견준다.
- 표시: 이력이 비었으면 "첫 기록", 직전과 같은 커밋이면 "같은 커밋 재실행", 조건이 다르면 "조건 바뀜", 성공 3회 미만이면 "표본 부족"이다.
- 멱등: 같은 실행 번호와 시도 번호를 다시 기록하면 줄을 더하지 않고 이미 있는 줄로 같은 비교를 낸다.

| 이력 브랜치                | 쓰는 실행                                                          |
| -------------------------- | ------------------------------------------------------------------ |
| `calibration-history`      | 주 1회 실행(schedule), develop에서 `history=prod`를 고른 수동 실행 |
| `calibration-history-test` | 그 밖의 수동 실행과 PR 브랜치 시험 실행                            |

이력 브랜치는 워크플로만 쓰고 손으로 고치지 않는다. 시험 실행은 운영 이력과 이슈 후보에 섞이지 않는다.

## 실제 지도와 실사용 값

| 이름                       | 종류             | 쓰는 곳                                              | 없을 때                                          |
| -------------------------- | ---------------- | ---------------------------------------------------- | ------------------------------------------------ |
| `NAVER_MAP_CLIENT_ID`      | Actions secret   | 실제 지도 빌드(`localhost:3000`)와 `real-*` 시나리오 | 실제 지도 시나리오를 건너뛰고 목 시나리오만 돈다 |
| `POSTHOG_PERSONAL_API_KEY` | Actions secret   | 운영 실사용 값 조회(`posthog-field.mjs`)             | 실행 요약에 "실사용 값 없음(키 없음)"            |
| `POSTHOG_PROJECT_ID`       | Actions variable | 위와 같음(579863)                                    | 위와 같음                                        |

- secret은 이 저장소의 schedule과 workflow_dispatch에서만 꺼낸다. 이 워크플로에는 pull_request 트리거가 없고, 포크에서 돌거나 다른 이벤트면 빈 값이라 지금처럼 목으로만 돈다.
- 값이 결과에 남지 않게 한다. `measure-android.mjs`가 원자료의 지도 SDK 주소(`ncpKeyId=`)와 키 값을 `***`로 가리고, `scrub-secrets.sh`가 이력 브랜치에 올리기 전과 아티팩트를 올리기 전에 결과 폴더를 다시 훑는다. 그래도 값이 남으면 그 단계가 실패하고 아티팩트를 올리지 않는다. Actions 로그의 secret 값은 GitHub가 가린다.
- 실사용 값: 운영 PostHog의 `first_listing_card_visible` 이벤트에서 `environment=production`인 최근 7일의 `time_ms` 중앙값과 p75를 `platform`, `connection_effective_type`별로 조회해, 실행 요약의 흉내 값과 에뮬레이터 웹뷰 값 표 아래에 배율과 함께 붙인다. 무리마다 표본이 20개 미만이면 값을 비우고, 모두 적거나 키가 없거나 조회가 실패하면 "실사용 값 없음(이유)"으로 적고 실패하지 않는다. 키는 조회 권한(`query:read`)만 있으면 된다.

### 네이버 콘솔의 localhost 등록

네이버 클라우드 콘솔의 Maps Application에 등록한 Web 서비스 URL에서만 이 키로 지도를 쓸 수 있다. 에뮬레이터 웹뷰는 `http://localhost:3000`을 열므로 이 주소가 등록되어 있어야 한다. 프론트 개발 서버의 기본 주소(`PORT` 기본 3000)와 같아 따로 더할 것이 없으면 그대로 쓴다. 등록이 없으면 지도 인증이 실패해 `real-*` 시나리오가 환경 오류로 남는다. 2026-11-26 실행에서 확인한 결과는 아래 "실행 기록"에 있다.

## 판정

`calibration-judge.mjs`가 숫자로만 판정한다.

1. 제외: 환경 오류(기기, 연결, 웹뷰 붙기)가 한 번이라도 있거나 성공이 3회 미만인 시나리오는 판정하지 않는다.
2. 의심: 최근 4회 중앙값보다 `max(300ms, 20%)` 넘게 느리면 성능 의심, 앱 오류(환경 오류가 아닌 실패)가 있으면 기능 의심이다.
3. 확인: 의심이 있으면 같은 에뮬레이터에서 이전 커밋(이력의 가장 최근 다른 커밋)을 따로 빌드해 4303으로 띄우고, 이전과 이번을 번갈아 5회씩 다시 잰다(`android/build-baseline.sh`). 이전 커밋도 이번 커밋의 목 핸들러로 답한다.
4. 결론: 다시 잰 차이가 문턱을 넘으면 "성능 이상 확인", 이번 커밋에서 다시 실패하면 "기능 실패 확인"이다. 재현되지 않거나 다시 잴 때 환경 오류가 나면 후보를 만들지 않는다.
5. 안정 키: `android-webview/<시나리오>/<perf|fix>/v<버전>/<조건 지문>/<이전 커밋 또는 오류 요지>`다. 같은 문제는 실행이 달라도 같은 키라 `issues.json`에 후보가 하나로 남고, 실행 목록만 늘어난다.

수동 실행의 `confirm` 입력은 `auto`(의심될 때만), `always`(시험용, `cold`와 `register`를 늘 다시 잼), `never`다.

## 이슈 게시

게시 대상은 팀 저장소(`woowacourse-teams/2026-jachwi-sunbae`) 하나이고, 작성자는 iftype이다.

- 게시 후보: 운영 이력의 주 1회 실행에서 확인된 후보만 `publishable`이다. 시험 실행의 후보는 늘 "무시"다.
- 형식: 팀 이슈 템플릿(`.github/ISSUE_TEMPLATE/issue.md`)의 배경, 작업 내용, 완료 조건, 참고 자료를 따른다. 제목은 `[FE][Perf] 앱 웹뷰 <시나리오>이 이전 커밋보다 느려졌다`나 `[FE][Fix] 앱 웹뷰 <시나리오>이 실패한다`다. 배경에 실측, 기대 동작, 재현 조건, 실행 링크를 적고, 본문 끝에 `<!-- jachwi-perf-key: <키> -->`를 둔다.
- 하지 않는 것: 라벨, 담당자, 멘션, 댓글. 본문에 멘션처럼 보이는 글자가 있으면 올리지 않는다.
- 중복: iftype이 올린 팀 이슈(열림, 닫힘)의 본문에서 키를 찾아, 같은 키가 있으면 "중복"으로 건너뛴다. 다시 돌려도 새 이슈가 생기지 않는다.

### 소유자 환경에서 올리기

팀 워크플로에는 개인 토큰을 넣지 않는다. 게시는 소유자가 통제하는 환경에서만 한다. 지금 쓰는 길은 소유자 PC의 gh 로그인이다.

```bash
# 저장소 루트에서. 먼저 계획만 본다(기본이 dry-run).
node .claude/skills/verify-jachwi/scripts/perf-issue.mjs
# 계획이 맞으면 올린다. gh 로그인 계정이 iftype이 아니면 아무것도 올리지 않는다.
node .claude/skills/verify-jachwi/scripts/perf-issue.mjs --publish
```

- 후보는 팀 저장소 `calibration-history` 브랜치의 `android-webview/issues.json`(공개 파일)에서 읽는다.
- `--publish`는 GitHub Actions의 팀 저장소 실행 안에서는 스크립트가 거부하고, 합성 후보 파일(`--candidates`)과 같이 주어도 거부한다.
- 기존 이슈를 읽지 못하면 중복을 막을 수 없어 올리지 않는다.
- 소유자 환경을 Actions로 옮기려면 iftype 개인 저장소의 워크플로와 그 저장소 secret에 둔 토큰으로만 한다. 토큰은 팀 저장소 이슈 쓰기만 되는 최소 권한(fine-grained면 팀 저장소의 Issues 읽기와 쓰기, 조직 승인 필요)으로 만든다. 이 설정은 아직 없다.

## 시험과 검증

- 단위 테스트: `frontend/test/scripts/calibration-history.test.ts`(이력 비교), `frontend/test/scripts/calibration-judge.test.ts`(의심, 확인, 안정 키, 멱등, 이슈 형식, 게시 갈래).
- 합성 장애 dry-run: 워크플로의 `Issue dry-run` 단계가 `fixtures/perf-issue-synthetic.json`과 `fixtures/perf-issue-existing-keys.json`으로 생성, 중복, 무시 갈래가 차례로 나오는지 보고, 다르면 실패한다.
- 수동 실행: develop에 이 워크플로가 있으면 Actions에서 `Android WebView Calibration`을 `history=test`, `confirm=always`로 돌린다. 이력과 후보는 시험 이력 브랜치에만 남는다.

## 한계

- 에뮬레이터는 실기기가 아니다. 러너 CPU(x86_64, KVM) 위라 저가 휴대폰보다 빠를 수 있고, 실행마다 흔들림이 커서 한 번의 값보다 최근 4회와 견줘 읽는다.
- 이미지의 WebView 124는 실사용 기기보다 오래됐다. 셸에는 RN, 네이티브 탭바, 푸시가 없다.
- 목 API라 실사용의 서버 응답 시간 차이는 보이지 않는다.
- 지도를 눌러 위치를 고르는 등록 길은 키가 있는 실행의 실제 지도 시나리오에서만 재고, 참고 값이라 판정하지 않는다. 고른 자리는 검색 핀 바로 아래라 검색한 주소와 정확히 같지 않다.
