# TypeScript 사용 기준

프론트엔드에서 TypeScript를 어떻게 쓰는지, 왜 그렇게 정했는지, 무엇이 그 기준을 강제하는지 적는다. 경로는 모두 `frontend/` 기준이다.

숫자는 2026-11-12 `develop`(`01112c2e`)에 이 문서를 넣은 변경(이슈 #660)을 더한 상태에서, 스토리(`*.stories.*` 133개)와 목(`src/app/mocks` 17개)을 뺀 `src` 531개 파일을 정규식으로 센 값이다. 테스트는 `test/`에 따로 있다.

## 1. 기준

구분 열의 뜻은 다음과 같다.

- **스타일**: 어느 쪽을 골라도 타입 검사 결과와 실행 동작이 같다. 읽는 사람이 한 가지 모양만 보도록 하나로 정한다.
- **안정성**: 어기면 컴파일러가 잡을 수 있던 오류가 실행 중으로 넘어간다.

| 대상                                                        | 끈 규칙                                               | 이유                                                                                             |
| ----------------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `src/global.d.ts`, `src/shared/lib/native-app/nativeApp.ts` | `consistent-type-definitions`                         | `Window`에 속성을 더하는 선언 병합은 `interface`로만 된다.                                       |
| `test/**`                                                   | `no-non-null-assertion`                               | 값이 없으면 그 줄에서 `TypeError`가 나 테스트가 실패하므로 막아도 얻는 것이 없다(49곳).          |
| `test/**`                                                   | `consistent-type-imports`의 `disallowTypeAnnotations` | `vi.mock`의 `importOriginal<typeof import('...')>()` 관용구를 쓴다(8곳).                         |
| `src/shared/lib/analytics/logging/withLogClick.tsx` 한 줄   | `no-explicit-any`                                     | 버튼과 링크처럼 요소마다 이벤트 타입이 달라 `MouseEvent<any>`로 받는다. 사유 주석이 코드에 있다. |

### 린트가 못 잡는 것

- `JSON.parse()`와 `response.json()`이 돌려주는 암묵적 `any`. `no-explicit-any`는 손으로 적은 `any`만 본다. 받는 변수에 `: unknown`을 적는다.
- `as` 단언 전체.
- 타입 정보가 필요한 규칙(`no-unsafe-assignment` 등). ESLint를 타입 정보 없이 돌리고 있어 켜지 않았다.

## 2. 타입을 믿을 수 있는 구간과 없는 구간

타입은 컴파일할 때만 있다. Babel(`@babel/preset-typescript`)이 타입을 지운 뒤의 번들에는 타입이 없고, 실행 중에 값의 모양을 확인하는 코드는 우리가 직접 쓴 것뿐이다. 그래서 타입이 참인 곳은 **우리 코드가 만든 값**과 **이미 검증을 지나온 값**까지다.

```text
  바깥(타입을 믿을 수 없다)            경계(unknown으로 받아 검증)              안쪽(타입을 믿는다)
  네트워크 응답, 브라우저 저장소,  →   parseData, 타입 가드, 파서          →   model 타입, 훅, 컴포넌트
  URL, 네이티브 앱, 서드파티 SDK       형식이 다르면 오류나 "없는 값"
```

| 구간 | 타입을 믿는가 | 우리 코드의 예                                                                                                                           |
| ---- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 안쪽 | 믿는다        | 파서가 돌려준 `PropertyDetail`을 훅과 컴포넌트가 다시 검사하지 않는다.                                                                   |
| 경계 | 믿지 않는다   | `apiRequest`는 `parseData: (value: unknown) => T`를 받아야만 `T`를 돌려준다. 저장소는 `const value: unknown = JSON.parse(...)`로 받는다. |
| 바깥 | 믿을 수 없다  | 서버가 필드를 빼고 배포해도, 이전 버전이 저장한 값이 남아 있어도, 사용자가 주소를 고쳐도 컴파일은 통과한다.                              |

경계에서 `as`를 쓰면 바깥 값이 검증 없이 안쪽 타입을 얻는다. 이 문서를 넣으면서 고친 `explorationJourney.ts`가 그 예다.

```ts
// 전: 저장소 값에 Journey 타입을 붙인 뒤 일부 필드만 확인했다. selectedLocation은 확인 없이 MapAddress가 됐다.
const value = JSON.parse(sessionStorage.getItem(KEY) ?? 'null') as Journey | null;

// 후: unknown에서 시작해 확인한 필드만으로 Journey를 만든다.
const journey = parseJourney(JSON.parse(sessionStorage.getItem(KEY) ?? 'null')); // (value: unknown) => Journey | null
```

## 4. 타입 검사가 일어나는 지점

| 순서 | 지점                     | 타입을 검사하는가                                                                                                                                                                                                                                     | 실패하면                                                                  |
| ---- | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 1    | 편집기                   | TypeScript 언어 서버가 `tsconfig.json`(`strict`)으로 검사한다.                                                                                                                                                                                        | 밑줄만 뜬다. 막지 않는다.                                                 |
| 2    | 개발 서버(`npm run dev`) | 하지 않는다. `babel-loader`의 `@babel/preset-typescript`는 타입을 지우기만 한다.                                                                                                                                                                      | 타입 오류가 있어도 화면이 뜬다.                                           |
| 3    | 테스트(`npm test`)       | 하지 않는다. Vitest도 타입을 지우고 실행한다.                                                                                                                                                                                                         | 타입 오류가 있어도 테스트가 통과할 수 있다.                               |
| 4    | `npm run typecheck`      | `tsc --noEmit`이 `src`와 `test`를 검사한다. 번들은 만들지 않는다.                                                                                                                                                                                     | 0이 아닌 코드로 끝난다.                                                   |

## 5. 스키마 라이브러리를 쓰지 않는 선택

`package.json`에 zod, valibot 같은 스키마 라이브러리가 없고, 응답 파서는 `readRecord`, `readString`, `readInteger` 같은 작은 함수(`src/shared/api/responseParsers.ts` 94줄)를 조합해 손으로 쓴다(`authParsers.ts`, `checklistParsers.ts`, `propertyParsers.ts` 합쳐 622줄). 얻는 것은 세 가지다. 의존성과 번들이 늘지 않는다(첫 화면 묶음은 `webpack.config.cjs`의 `performance` 설정으로 355KiB를 넘으면 빌드가 실패하고, 주석에 적힌 대로 이미 한도 가까이에 있다). 검증과 함께 화면 타입으로의 변환, 범위와 길이 확인을 같은 함수에서 한다. 파서가 평범한 함수라 뮤테이션 테스트 대상에 그대로 들어간다. 잃는 것도 있다. 타입과 파서를 따로 쓰므로 둘이 어긋날 수 있다. 파서가 필드를 빠뜨리면 반환 타입 때문에 `tsc`가 잡지만, 확인한 뒤 `as`로 좁히는 곳(예: `propertyParsers.ts`의 통근 상태)은 확인 코드가 타입과 맞는지를 `tsc`가 보지 못해 리뷰와 테스트에 기댄다. 필드가 늘 때마다 손으로 쓰는 줄이 늘고, 실패한 필드의 경로 같은 오류 정보도 직접 만들어야 한다. 팀이 스키마 라이브러리와 비교해 결정한 기록은 저장소와 커밋 기록에서 찾지 못했다. MVP 이관(`0915ce00`) 때부터 손으로 쓴 파서였고 그 방식을 이어 온 것이다.

## 6. LLM 설정

저장소 루트의 `AGENTS.md`와 `CLAUDE.md`(같은 내용)에 1절의 핵심과 이 문서 경로를 적었다. 에이전트가 쓴 코드도 사람 코드와 같은 `npm run lint`, `npm run typecheck`, CI를 지나므로, LLM 설정은 처음부터 맞게 쓰게 하는 안내이고 걸러 내는 것은 린트와 `tsc`다.

## 7. 남은 일

- 관리자 API 응답에 파서를 붙인다(`requestAdmin<T>`의 `as` 제거).
- `location.state`를 `as`로 읽는 5곳을 타입 가드로 바꾼다.
- `noUncheckedIndexedAccess`를 제품 코드(52개)부터 나눠 켠다.
- 타입 정보 린트(`no-unsafe-*`)를 켤지 정한다. 린트 시간이 늘어나는 것과 견줘야 한다.
