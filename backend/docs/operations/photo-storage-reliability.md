# 사진 저장소 신뢰성 검증

백엔드 신뢰성 개선 2단계 기록이다. 2026-11-24 기준이며 운영 배포는 실행하지 않았다.
1단계의 미커밋 변경과 기존 `.claude/`는 유지했다. 월세 수집본·체크리스트·전체 배포 및 복구 점검은 후속 단계다.

## 문제

기존 `PropertyPhotoService`는 파일을 올린 뒤 메타데이터를 저장하고, `store` 콜백 안에서 예외가 나면 파일을 삭제한다.
실제 MySQL 연결을 `beforeCommit`에서 종료하자 콜백이 반환된 뒤 COMMIT이 실패했고, DB 행은 없는데 원본·썸네일은 남았다.
보상 삭제 실패와 업로드 직후 프로세스 종료에는 파일 키를 다시 찾을 영속 기록도 없었다.

사진·매물 삭제는 S3 파일을 먼저 지웠다. 뒤의 SQL을 실패시키면 DB만 롤백되어 갤러리에 남은 사진의 파일이 사라졌다.
기존 사진의 썸네일 보충도 파일 전송과 메타데이터 반영 사이 중단에 대한 복구 기록이 없었다.

명세와 삭제 구현도 달랐다. 사용자는 이번 작업에서 다음 명세를 따르기로 확인했다.

- `POL-PHOTO-007`: 개별 사진은 논리 삭제하고 DB·파일을 보존한다. 조회·대표 지정·새 PDF에서 제외한다.
- `POL-AUTH-016`: 삭제한 매물과 탈퇴한 회원의 사진 파일은 삭제한 날부터 90일 보관 후 파기한다.

| 대안                                            | 장점                                                                   | 한계                                                                                                                |
| ----------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |

## 선택 이유와 구현

### 실패 업로드와 썸네일 보충

V22의 `photo_storage_cleanup_requests`에 원본·썸네일 키를 사진 트랜잭션 **시작 전에** 독립 커밋한다.
등록에 실패하면 파일을 보내지 않는다. 복구 기록에 회원·매물 FK를 두지 않아 주 트랜잭션의 잠금에 의존하지 않는다.

1. 입력과 사진 파일을 검증하고 썸네일을 생성한다.
2. 복구 기록을 커밋한다. 자동 정리는 1시간 뒤부터 가능하다.
3. 사진 트랜잭션에서 매물 소유권·사진 한도를 다시 검사하고 복구 행을 잠근다. 파일 전송 전에 기록이 없어졌으면 중단한다.
4. 원본·생성된 썸네일을 전송하고 사진 메타데이터·대표 사진을 저장한다.
5. 같은 사진 트랜잭션에서 복구 기록을 제거하고 커밋한다. 메타데이터와 복구 기록 제거는 함께 성공하거나 롤백된다.
6. SQL·파일 전송·최종 커밋 실패 시, 트랜잭션이 끝난 뒤 즉시 정리한다. 전송을 시작하지 않은 요청은 파일 삭제 없이 복구 기록만 제거한다.

정리기는 요청 행을 `FOR UPDATE SKIP LOCKED`로 잠그고, 파일 삭제와 정리 기록 갱신이 끝날 때까지 잠금을 유지한다.
같은 행을 잠근 업로드나 다른 정리 작업이 있으면 건너뛴다. 따라서 별도의 리스·UUID 없이도 이 경계에서 두 정리기가 겹쳐 쓰지 않는다.
정리 직전에 DB의 원본·썸네일 참조를 검사하며, 논리 삭제한 사진도 보관 대상이므로 참조로 취급한다.
커밋 성공 후 응답만 유실되어도 정상 사진을 지우지 않는다.

정리 실패는 기록을 유지하고 1·2·4분부터 최대 12시간 간격으로 재시도한다. 실패 횟수로 기록을 포기하지 않는다.
파일을 지운 뒤 정리 기록의 DELETE나 커밋이 실패해도 남은 기록으로 재시도한다.
호출자가 연 외부 트랜잭션에 참여 중이면 즉시 정리로 추가 연결을 점유하지 않고 다음 스케줄러 실행으로 넘긴다.

기존 사진의 썸네일 보충에도 같은 기록을 사용한다. 원본 다운로드와 이미지 생성은 트랜잭션 밖에서 끝낸다.
전송 직전에 활성 매물을 잠그고 사진 존재·썸네일 유무를 재확인한다. 실패 시 새 썸네일만 회수하고 원본은 보존한다.
같은 키의 미완료 복구 기록이 있으면 기록을 재사용하고 자동 정리 유예 시각을 갱신한다. 따라서 보상 삭제 실패 직후에도 같은 썸네일 보충을 재시도할 수 있다.

업로드 성공 기준은 바꾸지 않았다.

- 썸네일 **생성 불가**: 원본만 저장해 성공하며 조회는 원본으로 대체한다.
- 생성된 썸네일의 **업로드 실패**: 전체 업로드를 실패시키고 원본·썸네일 회수를 시도한다.
- 원본·사진 정보·대표 지정까지 커밋되어야 정상 사진으로 노출한다.

### 삭제와 90일 보관

개별 사진 삭제는 `deleted_at`만 기록하고 대표 지정을 제거한다. 목록·건수·단일 사진 조회·대표 후보에서 삭제 사진을 제외하므로 새 PDF에도 포함되지 않는다.
파일은 지우지 않는다. 개별 사진 삭제만으로 90일 파기를 예약하지 않으며, 부모 매물이나 회원이 삭제되면 그 보관 기준을 적용한다.
매물 삭제도 S3를 호출하지 않고 부모의 논리 삭제만 커밋한다. 삭제 SQL·커밋 실패는 파일을 손상시키지 않는다.

정리기는 매물 또는 회원의 삭제 시각이 현재 UTC 시각보다 90일 이상 지난 사진만 선택하고, 부모·사진 행을 잠근 뒤 조건을 다시 확인한다.
원본·썸네일 삭제를 마치면 `storage_purged_at`을 기록한다. 실패하면 `storage_purge_next_attempt_at`으로 5분 뒤 다시 시도하며 기록을 포기하지 않는다.
S3 성공 후 DB 완료 기록이 실패해도 다음 회차에 같은 파일을 다시 삭제해 마친다.
파일 파기 뒤에도 사진 메타데이터와 파기 완료 시각은 남긴다. 다른 업무 기록까지 포함하는 DB 개인정보 파기는 이번 단계에 구현하지 않았다.

## 검증 결과

실제 MySQL 8.4.10 Testcontainers를 사용하고 S3 경계는 파일 상태를 보유하는 저장소 대역으로 통제했다.
새 신뢰성 테스트에는 테스트 트랜잭션을 걸지 않았다. 기존 사진 서비스 테스트도 실제 서비스 커밋을 검증하도록 테스트 단위 트랜잭션을 제거하고 매번 DB를 초기화한다.
기존 로컬·운영 DB 및 실제 AWS S3 계정은 사용하지 않았다. 별도 수동 QA에는 전용 MySQL·MinIO 컨테이너와 실제 백엔드 JAR을 사용했다.

| 시나리오                      | 검증 방법·기대 결과                                                                             |
| ----------------------------- | ----------------------------------------------------------------------------------------------- |
| 실제 최종 COMMIT 실패         | 전송 중 등록한 `beforeCommit`에서 테스트 MySQL 연결을 KILL. 사진·대표 지정 롤백, 파일 회수      |
| 실제 커밋 성공 후 응답 유실   | 실물 트랜잭션을 커밋한 다음 대역에서 예외 주입. 정상 DB 사진·파일 보존                          |

| 메타데이터 INSERT 실패        | MySQL 트리거 오류. 메타데이터·대표 지정 롤백과 파일 회수                                        |

| 90일 경계                     | Clock으로 90일 직전·정확한 경계 제어. 매물·회원 삭제 모두 경계에서만 파기                       |
| 보관 파일 파기 실패           | 저장소 실패와 DB 완료 UPDATE 실패 각각 주입. 재시도로 완료 기록                                 |
| 썸네일 보충 COMMIT 실패       | 실물 MySQL 연결 종료. 새 썸네일만 회수하고 원본·기존 메타데이터 보존                            |
| 연결 풀 크기 1                | 일반 업로드·실패 복구가 하나의 연결을 순차 재사용. 실제 두 작업자의 경합 테스트만 두 연결 사용  |
| V21 → V22                     | 기존 사진의 모든 컬럼·삭제 시각·대표 지정 보존, 복구 테이블은 빈 상태로 생성                    |

수정 전 최초 재현은 4개 중 3개가 실패했다. 업로드 최종 커밋 실패 시 파일이 남았고, 사진·매물 삭제 SQL 실패 시 파일이 사라졌다.
추가로 중첩 복구 트랜잭션은 연결 풀 크기 1에서 `CannotCreateTransactionException`을 재현했으며, 등록 커밋을 사진 트랜잭션 앞으로 옮겼다.
최초 집중 검사에서는 새 신뢰성 테스트 18개, 기존 사진 서비스 11개·썸네일 보충 3개, 마이그레이션 19개와 아키텍처 검사를 포함해 72개가 모두 통과했다.
이후 정리 기록이 남은 보충 재시도에서 `DuplicateKeyException`을 재현하고 기록 재사용을 보완했다. 보완 후 신뢰성 테스트 19개·기존 사진 서비스 11개·썸네일 보충 3개가 모두 통과했다.
Java 21로 `backend`에서 최종 전체 검사를 실행했다.

```bash
./gradlew testAll --no-daemon
```

- `BUILD SUCCESSFUL`, 종료 코드 0. 217개 테스트 클래스에서 전체 1,960개 중 통과 1,959개, 실패·오류 0개, 건너뜀 1개.
- 건너뛴 항목은 `BEDROCK_LIVE_IMAGES`를 지정해야 실행되는 기존 Bedrock 실호출 테스트다.
- 사진 신뢰성 19개, 기존 사진 서비스 11개·썸네일 보충 3개, 마이그레이션 19개가 모두 통과했다. 1단계 Outbox·탈퇴 트랜잭션과 아키텍처 검사도 통과했다.
- 종료 정리 중 이미 종료된 테스트 DB에 대한 Hikari 연결 경고가 출력됐지만 테스트 실패는 없었다.
- 루트에서 `npm run format:docs`, `npm run format:docs:check`와 `git diff --check`를 실행했다. 기존 변경은 보존하고 디버깅 임시 파일은 제거했다.

별도 임시 MySQL·MinIO와 백엔드 JAR을 기동하고 `curl`로 다음 HTTP 흐름을 확인했다.

| 흐름                  | 실제 결과                                                        |
| --------------------- | ---------------------------------------------------------------- |
| 익명 로그인·매물 생성 | HTTP 200·201                                                     |

| 부모 매물 논리 삭제   | HTTP 204, 남은 사진 콘텐츠 접근은 404, 파일 4개 유지             |

이후 부모의 삭제 시각을 91일 전으로 지정하고 고아 파일 1개와 기한이 지난 정리 요청을 전용 DB·MinIO에 구성했다.
정리기를 활성화한 새 백엔드 프로세스의 실제 스케줄러 실행 뒤 MinIO 객체 5개가 모두 사라지고, 정리 요청은 0개·사진 파기 완료 표시는 2개가 됐다.
QA가 끝난 뒤 전용 프로세스·컨테이너·임시 파일을 제거했다. 실제 S3 계정이나 기존 로컬 데이터는 사용하지 않았다.

## 적용과 복구

기본·로컬 프로필은 정리기를 끄고 dev·prod는 켠다. `PHOTO_CLEANUP_ENABLED`로 덮어쓸 수 있으며 변경 후 재기동해야 한다.
1분 간격으로 실패 업로드 후보 최대 20개와 보관 기간 만료 사진 최대 20개를 조회한다. 조회 후보 수는 파일 삭제 성공 건수를 의미하지 않는다.

운영 적용 전에는 `PHOTO_CLEANUP_ENABLED=false`로 기동해 V22와 파기 후보를 먼저 확인한다.
기존 삭제 사진·매물·회원과 버킷 상태를 확인한 뒤 정리기를 활성화한다. 구버전 사진 API는 파일을 즉시 삭제하므로 보존 정책 적용 시 구버전과 혼용하지 않는다.
운영 배포·정리 작업 활성화는 이번 작업에서 실행하지 않았다.

```sql
SELECT COUNT(*) AS cleanup_pending, MIN(created_at) AS oldest_request
FROM photo_storage_cleanup_requests;

SELECT COUNT(*) AS expired_photo_files
FROM property_photos ph
JOIN properties p ON p.id = ph.property_id
JOIN members m ON m.id = p.member_id
WHERE ph.storage_purged_at IS NULL
  AND (p.deleted_at <= UTC_TIMESTAMP(6) - INTERVAL 90 DAY
       OR m.deleted_at <= UTC_TIMESTAMP(6) - INTERVAL 90 DAY);
```

복구 기록은 데이터 복원 때도 함께 보존한다. 이력과 추가 컬럼을 지우거나 정리 테이블을 임의로 비우지 않는다.
구버전으로 코드만 롤백하면 새 복구 요청 처리가 멈추고 즉시 파일 삭제 동작이 되돌아오므로, 이 보완이 포함된 리비전으로 복구한다.

## 남은 한계

- 도입 전에 이미 기록 없이 남은 고아 파일은 자동 발견하지 못한다. 기존 파일을 조사할 때는 S3 Inventory와 보관 중인 논리 삭제 사진까지 포함한 DB 키를 대조해야 하며, 이번에 버킷 전체 탐색·일괄 삭제는 구현하거나 실행하지 않았다.
- 프로세스 중단 테스트는 영속 기록·파일만 남은 상태에서 새 처리기를 구성한다. 실제 S3 서버의 지연 전송 완료와 OS 강제 종료를 함께 실험하지 않았다. 1시간 유예 후에도 서버 측 늦은 PUT이 완료되는 극단적인 경우까지 보장하지 않는다.
- 파일 업로드·정리·90일 파기는 일부 구간에서 DB 행 잠금과 연결을 보유한다. 외부 트랜잭션이 이미 연결을 점유한 채 업로드·보충을 호출하면 영속 기록의 독립 커밋에 두 번째 연결이 필요하다. 현재 HTTP 업로드·관리자 보충 진입점은 외부 트랜잭션을 열지 않는다.
- S3 버전 관리가 켜진 버킷에서 versionId 없는 DeleteObject는 이전 버전을 지우지 않고 삭제 마커를 만들 수 있다. 이전 버전과 백업의 실제 보존·파기 설정은 별도 확인이 필요하며 이번에 변경하지 않았다. [AWS DeleteObject 문서](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObject.html)
- 파기 완료 컬럼은 현재 키에 대한 저장소 삭제 완료를 나타낸다. 모든 S3 버전·백업이나 다른 DB 개인정보의 완전 파기를 증명하지 않는다.
- 기존 버그로 이미 사라진 파일은 코드 변경만으로 복원할 수 없다. 버전·백업이 있는지 확인해야 한다.
- 처리량·응답 시간·장애율의 개선 수치는 측정하지 않았다.
