# 월세 수집본 교체 신뢰성 검증

## 범위와 유지한 정책

`RentalImportService`의 수집본 전체 교체와 `AdminLegalDongImportService`의 관할 법정동 연결표 교체가 같은 월세 시세를 갱신하는 경로를 확인했다.
기존 데이터 선택 정책과 API 응답 계약은 유지했다.

- 같은 dataset의 적재는 기존 `rental_datasets` 행 잠금으로 직렬화한다. 최초 적재도 포함한다.
- 파일 해시·조회 기간·수집 시각이 같은 수집본은 DB 거래 건수를 확인하고 `UNCHANGED`로 생략한다.
- 현재보다 이전 시점에 수집한 자료는 거절한다. 수집 시각이 같고 내용이 다른 경우의 기존 교체 동작은 바꾸지 않았다.
- 법정동·거래·수집본 메타데이터·행정동 월세 시세는 기존 `TransactionTemplate` 안에서 함께 커밋하거나 롤백한다.
- 시세의 메모리 캐시는 기존처럼 웹 서버가 기동할 때 읽는다. 적재만으로 실행 중인 서버의 캐시가 바뀌지는 않는다.

## 문제

월세 적재끼리의 잠금과 트랜잭션은 이미 구현돼 있었다. 실제 결함은 같은 시세를 갱신하는 연결표 적재 경로에서 재현됐다.

1. 월세 적재가 dataset 행을 잠그고 새 거래와 메타데이터를 저장한다. 아직 커밋하지 않는다.
2. 연결표 적재가 dataset 잠금 없이 행정동을 조회해 이전 DB 상태의 일관 읽기 스냅샷을 만든다.
3. 월세 적재가 새 거래와 새 시세를 커밋한다.
4. 연결표 적재가 연결표를 교체하고, 이전 스냅샷의 거래로 시세를 다시 계산해 커밋한다.

수정 전 MySQL 테스트에서는 거래와 수집본은 새 자료인데 시세만 이전 금액으로 돌아갔다.
합성 거래 5건의 월세를 450,000원에서 600,000원으로 바꿨을 때 최종 시세가 450,000원으로 남아 테스트가 실패했다.

MySQL의 `REPEATABLE READ`에서는 같은 트랜잭션의 일관 읽기가 처음 설정한 스냅샷을 사용한다.
따라서 시세 저장 직전에만 잠금을 얻어서는 앞선 조회가 만든 오래된 읽기 상태를 해결할 수 없다.
근거: [MySQL 일관 읽기](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html).

## 대안과 선택 이유

| 대안                                              | 판단                                                                                                                 |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 연결표 적재도 첫 조회 전에 기존 dataset 행을 잠금 | 선택. 이미 사용하는 직렬화 기준을 두 갱신 경로가 공유하고, 별도 스키마나 분산 잠금 없이 오래된 스냅샷 생성을 막는다. |
| 시세 삭제·저장 시점의 행 잠금만 사용              | 거래를 읽는 스냅샷이 먼저 만들어질 수 있어 부족하다. 기존 실패 시나리오를 해결하지 못한다.                           |
| 트랜잭션 격리 수준 변경                           | 기존 격리 계약까지 넓게 바꾸지 않고 공통 잠금으로 해결할 수 있다.                                                    |
| 별도 잠금 테이블·외부 분산 잠금 도입              | 기존 dataset 행이 같은 책임을 수행하므로 추가하지 않았다.                                                            |

`AdminLegalDongImportService.importLinks()`의 첫 DB 작업으로 `JdbcAdminDongRentRepository.lockDatasetForRefresh()`를 호출한다.
이 메서드는 월세 적재와 같은 기본 dataset 키를 `INSERT ... ON DUPLICATE KEY UPDATE`한다.
신규 행의 INSERT와 기존 기본키 행의 중복 UPDATE 모두 배타 잠금을 얻고, 연결표 교체와 시세 계산 트랜잭션이 끝날 때까지 유지한다.
근거: [MySQL 문장별 잠금](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html).

월세 수집본이 없는 DB에서는 잠금용 행만 만들어지고, 해시가 비어 있으므로 기존 조회는 이를 적재 완료된 수집본으로 취급하지 않는다.
이후 첫 월세 적재가 같은 행을 채운다. 연결표 적재가 실패하면 잠금용 신규 행도 롤백된다.
기존 월세 적재의 `FOR UPDATE`, 생성자 계약과 아키텍처 동결 기준은 그대로 유지했다. 이 단계의 스키마 변경은 없다.

## 검증 결과

### 실제 MySQL 회귀 테스트

`RentalImportServiceTest`는 MySQL 8.4.10 Testcontainers에서 테스트 자체의 롤백 트랜잭션 없이 실행한다.
기존 7개 검증을 유지하고 장애·동시성 시나리오 11개를 추가해 총 18개가 통과했다.
관련 시세 서비스·아키텍처 검사를 합친 실행도 42개 모두 통과했다.
전체 `testAll`은 217개 클래스, 1,971개 테스트 중 1,970개 성공, 실패·오류 0개, 생략 1개였다.
생략된 항목은 기존 `BedrockPropertyExtractorLiveTest`의 실제 외부 서비스 호출 테스트다.

장애 검증은 `legal_dongs`, `rental_datasets`, `rental_transactions`, `admin_legal_dongs`, `admin_dong_rents`의 정렬된 전체 행을 비교했다.
거래 ID, 해시, 수집·적재 시각, 건수, 시세와 기간을 포함한다. 자동 증가 번호의 연속성을 보장하는 검증은 아니다.
연결 종료는 테스트 컨테이너의 작업 연결에만 적용했다.

재현 명령은 `backend`에서 실행한다. Java 21과 Docker가 필요하다.

```bash
./gradlew test --tests 'com.jachwisunbae.rental.service.RentalImportServiceTest' --tests 'com.jachwisunbae.rental.service.AdminDongRentServiceTest' --tests 'com.jachwisunbae.architecture.*' --no-daemon
./gradlew testAll --no-daemon
```

### 패키징한 실제 적재 명령 검증

2026-11-24에 별도 MySQL 8.4.10 컨테이너와 합성 거래 5건을 사용해 패키징된 JAR의 `RentalImportCommand`를 실제 프로세스로 실행했다.

- 같은 자료로 동시에 실행한 두 명령이 각각 `IMPORTED`, `UNCHANGED`로 종료했다.
- 시세 INSERT 오류를 주입한 교체 명령은 종료 코드 1을 반환했고, 위 다섯 테이블은 교체 전 상태와 일치했다.
- 오류를 제거한 재실행은 `IMPORTED`로 종료했고, 거래 5건과 시세 모두 600,000원으로 일치했다.
- 이전 수집본은 종료 코드 1로 거절됐으며, 최신 데이터는 유지됐다.
- 같은 수집본의 재시도는 `UNCHANGED`였고 거래 ID와 메타데이터를 포함한 DB 상태가 유지됐다.

이 금액과 건수는 테스트 입력·검증값이다. 운영 처리량이나 성능 측정값이 아니다.
수동 검증용 컨테이너와 임시 파일은 검증 후 제거했다. 기존 로컬 DB와 운영 DB는 사용하지 않았다.

## 실패 후 확인과 재실행

1. 오류 로그와 `rental_datasets`의 파일 해시·기간·수집 시각·`row_count`, 실제 거래 건수, `admin_dong_rents`의 기간을 확인한다.
2. SQL 오류나 연결 종료로 롤백됐다면 원인을 해결한 후 같은 입력과 옵션으로 새 보고서 경로에 재실행한다.
3. 커밋 여부가 불명확하면 먼저 DB를 확인한다. 이미 같은 자료가 커밋됐다면 같은 입력의 재실행은 건수 확인 후 `UNCHANGED`가 된다.
4. 더 최신 자료가 이미 적재됐다면 이전 수집본 거절을 우회하지 않는다. 수집 시각이나 해시를 임의로 바꿔 복구하지 않는다.
5. DB 적재 결과를 확인한 뒤 기존 배포 절차에 따라 웹 서버를 재시작해 시세 캐시를 반영한다.

## 남은 한계

- 이 검증은 같은 기본 dataset의 월세 교체와 연결표 적재를 대상으로 한다. 행정동 경계 전체 교체 등 다른 적재 작업의 동시 실행까지 검증한 것은 아니다.
- 잠금은 첫 일관 읽기 전에 얻어야 한다. 향후 두 진입점을 이미 조회를 수행한 외부 트랜잭션에서 호출하면 그 트랜잭션의 읽기 상태까지 다시 검토해야 한다.
- 구버전 연결표 적재 프로세스는 공통 잠금을 사용하지 않는다. 신구 버전이 섞인 동안 연결표 적재와 월세 교체를 겹쳐 실행하지 않는다.
- DB 커밋과 로컬 JSON 보고서 저장은 하나의 트랜잭션이 아니다. 보고서 오류만으로 DB 적재 실패를 단정하지 않고 DB를 확인한다.
- 잠금 대기 시간 초과와 교착 상태의 자동 재시도 정책은 추가하지 않았다. 오류는 호출자에게 전달하며, 재실행 시 기존 수집본 검증을 다시 수행한다.
- COMMIT 검증은 실제 작업 연결 종료에 의한 롤백이다. DB 서버 강제 종료·스토리지 장애·복제 전환이나 운영 규모의 처리 시간은 측정하지 않았다.
- 실행 중인 서버의 시세 캐시를 자동 갱신하는 기능은 추가하지 않았다. 운영 배포와 데이터 복구 실행도 수행하지 않았다.
