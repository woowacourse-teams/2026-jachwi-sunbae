# 체크리스트 저장 신뢰성 검증

## 문제

현재 항목 상태 API는 토글이 아니라 상태 지정이다. 화면이 현재 선택과 같은 버튼을 누르면 `UNCONFIRMED`를 계산해 보내지만, 서버는 요청받은 상태를 그대로 저장한다.
메모 저장도 요청값으로 메모 컬럼만 바꾼다. 따라서 중간에 다른 변경이 없는 동일 요청 반복은 이미 DB 상태가 멱등이다.

다만 요청에 버전이 없으면 지연된 이전 저장과 새 선택을 구분하지 못한다.
수정 전 실제 MySQL에서 `GOOD → CAUTION → 이전 GOOD 재전송`이 최종 상태를 `GOOD`으로 되돌리는 것을 재현했다.
오래된 저장을 거절하는 회귀 테스트는 기존 코드에서 실패했다.

## 대안과 선택 이유

| 대안                          | 판단                                                                                                                              |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 마지막으로 처리한 요청을 저장 | 기존 동작이다. 지연된 이전 요청이 새 선택을 덮어쓸 수 있다.                                                                       |
| 상태·메모별 버전 검사         | 선택. 오래된 변경을 거절하면서 독립적인 상태 저장과 메모 저장은 함께 성공할 수 있다.                                              |
| 항목 전체의 단일 버전         | 상태와 메모가 서로 다른 컬럼인데도 불필요하게 충돌한다.                                                                           |
| 모든 요청에 멱등성 키 추가    | 현재 상태 지정의 단순 재시도를 위해 별도 영수증 저장소를 만들 필요는 없다. 서로 다른 요청의 선후 관계도 키만으로 해결되지 않는다. |

2026-11-24 사용자 결정: **오래된 저장은 400 오류로 거절하고 최신 값을 다시 조회해 사용자가 재선택한다.**
`409`를 사용하지 않는 기존 API 컨벤션을 따랐다. 공개 계약은 변경된 Swagger를 기준으로 한다.

## 구현

- V23이 기존 항목에 `status_version`, `memo_version`을 각각 0으로 추가한다. 기존 상태·메모·식별자는 유지한다.
- 항목 조회 응답은 `statusVersion`, `memoVersion`을 제공한다. 상태·메모 저장은 해당 컬럼의 조회 버전을 `expectedVersion`으로 받으며, 누락·음수를 거절한다.
- 기존 `SELECT ... FOR UPDATE`로 얻은 최신 항목에서 버전을 비교한다. 값과 해당 버전은 같은 트랜잭션에서 저장한다.
- 현재 값과 같은 요청은 새 쓰기와 버전 증가 없이 성공한다. 이미 저장된 값의 재시도를 충돌로 취급하지 않는다.
- 현재와 다른 값을 저장하려는데 버전이 다르면 `PROPERTY_CHECKLIST_ITEM_CONFLICT`로 거절한다. 상태 변경은 메모 버전을, 메모 변경은 상태 버전을 증가시키지 않는다.
- 프론트엔드는 사용자가 동작한 시점의 버전을 요청에 포함한다. 충돌 후 최신 버전으로 자동 재전송하지 않는다.
- 충돌이면 상세·집계·매물 목록을 다시 조회하고 다시 선택하도록 안내한다. 메모 초안은 현재 화면에 보존하며, 서버의 최신 메모를 함께 보여주고 명시적인 재저장을 받는다.
- 늦게 도착한 성공 응답도 화면에 이미 있는 더 높은 버전을 덮어쓰지 않는다.

상태·메모 API에는 멱등성 키를 추가하지 않았다. 양식 생성·사진 업로드 등 별도 생성 명령의 응답 재생이나 중복 생성 방지를 이번 항목 저장의 보장으로 확장하지 않는다.
양식 교체로 항목 ID가 바뀌면 이전 ID를 사용하는 요청은 기존처럼 리소스 없음으로 처리된다. 양식 교체·데이터 보존 정책은 변경하지 않았다.

## 검증 결과

- 실제 MySQL 8.4.10의 항목 서비스 테스트 9개 통과. 테스트 자체의 자동 롤백을 제거해 실제 커밋을 검증했다.
- 같은 상태·메모의 반복 요청에서 전체 항목 행이 동일하고, 새 항목이나 버전 증가가 없음을 확인했다.
- 오래된 상태와 메모 재전송은 거절되고 최신 값·버전이 유지됐다.
- 두 JDBC 연결로 실제 잠금 대기를 관찰했다. 서로 다른 컬럼의 동시 저장은 모두 보존되고, 같은 컬럼의 이전 버전 저장은 거절됐다.
- 최종 커밋 직전 테스트 작업 MySQL 연결을 종료하면 상태·메모·두 버전이 기존 전체 행으로 함께 롤백됐다.
- V22 데이터에서 V23으로 실제 마이그레이션해 기존 기록 보존과 버전 0 초기화를 확인했다. 기존 기준선·아키텍처 검사도 통과했다.
- Node 22.23.1에서 프론트엔드 전체 223개 파일, 1,487개 테스트 통과. 충돌 후 조회·자동 재전송 없음·늦은 응답 차단을 기존 테스트에 추가했다. lint·typecheck도 통과했다.
- 별도 MySQL·MinIO·패키징한 JAR를 띄워 실제 HTTP에서 버전 누락 400, 동일 값 재시도 성공, 오래된 변경 400과 최신 값 유지를 확인했다.
- 별도 브라우저 프로필에서 실제 프론트엔드와 API를 연결했다. 다른 작업자가 값을 바꾼 뒤 상태·메모를 저장하면 400과 재조회가 발생했고, 최신 값으로 재선택·명시적 메모 재저장하면 200으로 저장됐다. 작성 중인 메모 초안이 충돌 직후 유지됨을 확인했다.
- 데스크톱 1440px와 모바일 390px에서 충돌 안내와 최신 메모·재저장 버튼을 확인했다. 운영 데이터·사용자 브라우저 프로필은 사용하지 않았다.

## 남은 한계와 배포 조건

- 버전 필수 요청은 기존 클라이언트와 계약이 다르다. 백엔드·프론트엔드를 함께 전환하고 구버전 서버와 섞어 쓰지 않는다. 구버전 서버는 버전을 검사하지 않는다.
- 구버전 화면은 버전 없는 저장이 실패하므로 새로고침·앱 WebView 갱신을 안내한다. 호환성을 이유로 버전 없는 쓰기를 허용하지 않는다.
- 초안 보존은 현재 편집 화면의 메모 상태다. 브라우저 종료·새로고침·반응형 레이아웃 전환을 넘어 초안을 영구 보관하는 기능은 추가하지 않았다.
- 같은 값의 성공은 DB 상태의 멱등성이다. 모든 응답의 재생, 분석 이벤트의 정확히 한 번 전송이나 별도 생성 API의 멱등성을 보장하지 않는다.
- 네트워크 유실 후 최신 값이 달라졌다면 기존 요청을 자동 덮어쓰지 않는다. 최신 내용을 다시 확인하고 사용자가 저장해야 한다.

배포·롤백과 데이터 복구는 [배포](deployment.md), [롤백](rollback.md), [DB 마이그레이션](database-migrations.md) 절차와 함께 확인한다.
