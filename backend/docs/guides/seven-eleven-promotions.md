# 세븐일레븐 행사상품 연동 실험

## 출처와 실행 조건

출처는 [세븐일레븐 공식 홈페이지의 이달의 증정할인](https://www.7-eleven.co.kr/product/presentList.asp)이다. 사용자가 전달한 고객센터 답변인 **공식 홈페이지 출처 표시, 하루 1회 연동** 조건으로 구현한다. 상품 이미지 파일은 다운로드하지 않고 공개 URL만 저장한다.

수동 명령은 공식 출처를 출력한다. 기존 `GET /api/promotions?brand=SEVEN_ELEVEN` 응답에는 `X-Promotion-Source: https://www.7-eleven.co.kr/product/presentList.asp` 헤더를 붙인다. JSON 구조는 유지한다. 향후 화면에 사용할 때도 이 공식 홈페이지 출처를 표시해야 한다. 이번 범위에는 프론트엔드가 없다.

`test-con`에서 수행한 로컬 실험이다. Issue·PR·브랜치 생성, 병합, 배포와 기존 로컬·dev·prod DB 변경은 수행하지 않았다. DB 검증은 새 일회용 Testcontainers MySQL에서만 수행한다. 기존 이마트24 커밋은 유지하고, 세븐일레븐 연동 변경은 별도 커밋에 포함한다.

## 실제 확인한 요청

2026-10-27(KST)에 공식 HTML을 직접 요청해 확인했다. 웹 검색 도구에서는 시간 초과였으나 로컬 HTTPS 요청은 HTTP 200과 UTF-8 HTML을 반환했다. 참고 오픈소스의 대량 요청 크기나 가격 추측 규칙을 복사하지 않았다.

첫 화면은 다음 요청으로 받는다. 최초 1+1 화면은 GET으로 확인했고 다른 탭 전환은 공식 `fncTab()`과 같이 POST로 확인했다. Java Client는 네 탭 모두 POST한다.

```http
POST https://www.7-eleven.co.kr/product/presentList.asp
Content-Type: application/x-www-form-urlencoded

pTab=1
```

추가 상품은 공식 페이지의 `fncMore()`에 있는 요청을 사용한다.

```http
POST https://www.7-eleven.co.kr/product/listMoreAjax.asp
Content-Type: application/x-www-form-urlencoded

intPageSize=10&intCurrPage=2&cateCd1=&cateCd2=&cateCd3=&pTab=1
```

| pTab | 공식 화면 | 공통 행사 유형                          | 더보기 크기 | 확인 범위                      |
| ---- | --------- | --------------------------------------- | ----------- | ------------------------------ |
| 1    | 1+1       | `ONE_PLUS_ONE`                          | 10          | 첫 화면과 2~66페이지 실제 응답 |
| 2    | 2+1       | `TWO_PLUS_ONE`                          | 10          | 첫 화면 실제 상품 13건         |
| 3    | 증정행사  | 미지원, 비어 있지 않으면 전체 수집 실패 | 3           | 첫 화면과 Ajax가 모두 0건      |
| 4    | 할인행사  | `SALE`                                  | 10          | 첫 화면 실제 상품 13건         |

행사 탭 3의 존재와 다른 유형이라는 사실은 확인했지만 실제 증정 상품·구매 조건은 확인하지 못했다. 현재 0건은 정상 빈 탭으로 처리한다. 이후 상품이 나타나면 1+1·2+1로 추측하거나 누락하지 않고 브랜드 전체 수집을 실패시켜 기존 DB를 유지한다. 실제 카드와 조건을 확보한 뒤 `GIFT` 등을 도입할 수 있다. 이번에는 공통 `PromotionType`에 사용하지 않는 타입을 추가하지 않았다.

## 페이지 처리

- 첫 화면의 `#listUl`에 제목 카드·상품 카드·MORE가 함께 있다. 일반 탭의 실제 상품은 13건이며 `#intPageSize` 값도 13이다. 현재 빈 증정 탭의 값은 7이다.
- 첫 화면 스크립트의 `var intTotalCount`와 숨김 `#pTab`, `#cateCd1~3`, `#intPageSize`를 검증한다. 중복된 전체 수 선언은 값이 같아야 한다.
- 첫 화면 뒤에는 **Ajax 2페이지부터** 순회한다. 관찰한 Ajax 1페이지는 첫 화면의 앞 3건을 제외한 10건이었다. Ajax 1페이지만 시작점으로 사용하면 상품을 누락한다.
- 실제 Ajax 2~66페이지는 매번 추가 10건을 반환했다. 이전 목록 전체를 포함하는 누적 HTML이 아니다. 화면은 응답 조각을 기존 목록에 append한다.
- Ajax의 `#listPage`는 다음 번호이므로 요청 번호+1인지 확인한다. `#listCnt`는 일부 실제 응답에서 카드 누적 수와 달랐다. 예를 들어 첫 화면부터 103건을 받은 시점의 값이 99였다. 숫자 형식은 확인하지만 이 값을 종료 기준으로 쓰지 않는다.
- 첫 화면의 전체 수에서 실제 받은 카드 수를 빼고, 다음 응답 수가 `min(더보기 크기, 남은 수)`인지 검증한다. 정확히 전체 수를 채워야 성공이다. 탭당 최대 250페이지를 넘으면 실패한다.
- 누적 응답처럼 카드 수가 커지거나, 중간 빈 목록·잘못된 페이지·누락된 필드·통신 실패가 발생하면 부분 결과를 반환하지 않는다.

2026-10-27 실험에서는 시간 초과로 마지막 페이지의 실제 응답을 확보하지 못했다. 남은 수만큼 반환된다는 종료 규칙은 첫 화면 총수와 관찰한 더보기 계약에 기초한 구현이며 마지막 짧은 페이지는 fixture로 검증했다. Ajax 응답에는 전체 수가 없어 수집 도중 같은 개수의 상품 교체까지 탐지할 수는 없다.

## HTML 파싱과 카테고리

| 항목         | 실제 요소                        | 처리                                                  |
| ------------ | -------------------------------- | ----------------------------------------------------- |
| 첫 화면 상품 | `#listUl` 바로 아래 상품 `li`    | 제목·MORE와 중첩 배지 li를 제외                       |
| Ajax 상품    | 응답 body 바로 아래 상품 `li`    | MORE를 제외하고 요청당 카드 수 검증                   |
| 상품명       | `.infowrap .name`                | 공백 정리, 빈 이름 거부                               |
| 판매가격     | `.infowrap .price`의 판매가 span | 쉼표 정수 검증, `del`·`s` 정상가 제외, 정수 범위 검증 |
| 이미지       | `.pic_product img[src]`          | 빈 src 거부, 절대 HTTP(S) URL로 변환                  |
| 행사 유형    | `.tag_list_01 > li`              | 요청 탭과 1+1·2+1·할인 배지를 대조                    |

할인 첫 상품 `남양)딸기에몽190ml`의 실제 판매가는 1,400원이다. 삭제된 옛 마크업 주석에는 정상가 1,600원과 판매가가 함께 있어, 주석의 `.price_list`나 첫 번째 숫자를 가격으로 선택하지 않는다. 가격이 없거나 잘못되면 0으로 만들지 않고 실패한다.

`cateCd1~3`는 숨김 입력의 설명상 대·중·소분류 코드다. 스크립트에는 `presentListCategoryAjax.asp`를 호출하는 분류 코드도 남아 있다. 그러나 확인한 행사 목록·상품 카드와 상세 페이지 표본의 분류 값은 비어 있었고, 사용 가능한 분류 선택 화면·코드 매핑을 확보하지 못했다. 분류 Ajax의 실제 계약은 미확인이다. **공식 사이트 전체에 카테고리가 없다고 단정하지 않는다.**

따라서 세븐일레븐은 공통 `ProductCategory.UNKNOWN("미분류")`로 저장한다. 이름 키워드·AI 분류를 사용하지 않는다. 이마트24의 기존 4개 분류와 수집 로직은 유지한다. 기존 VARCHAR 컬럼으로 저장할 수 있어 테이블·마이그레이션은 추가하지 않는다.

## 기존 기능 연결

| 클래스                              | 책임·변경                                                                          |
| ----------------------------------- | ---------------------------------------------------------------------------------- |
| `SevenElevenPromotionTab`           | 공식 탭 코드·제목·더보기 크기                                                      |
| `SevenElevenPromotionClient`        | RestClient POST·form·UTF-8·요청 간 1초·연결 3초/응답 30초 제한                     |
| `SevenElevenPromotionParser`        | Jsoup 순수 파싱·메타데이터·필수 필드 검증                                          |
| `SevenElevenPromotionFetcher`       | 네 탭의 첫 화면과 추가 페이지를 모두 조합, 브랜드 `SEVEN_ELEVEN`                   |
| `PromotionFetcher`                  | `brand()` 식별 추가. 이마트24는 `EMART24` 반환                                     |
| `PromotionCollectionService`        | Fetcher 목록 주입, `collect()` 전체 브랜드 순회, `collect(brand)` 특정 브랜드 실행 |
| `PromotionCollectionScheduler`      | 기존 KST 매일 4시 작업에서 Service의 전체 브랜드 수집 호출 재사용                  |
| `JdbcPromotionProductRepository`    | SQL 변경 없이 브랜드별 원자적 교체·조회 재사용                                     |
| Controller·QueryService·DTO         | 기존 조회 재사용. 출처 헤더·UNKNOWN 설명 추가                                      |
| `SevenElevenLocalCollectionCommand` | 개발용 fixture·실제 수집·저장된 응답 재생을 일회용 MySQL과 연결                    |

별도 Factory·Registry·배치 프레임워크를 추가하지 않는다. Service는 등록된 Fetcher에서 브랜드를 선택하며 같은 브랜드의 중복 등록을 거부한다. 전체 실행은 브랜드별 예외를 기록한 뒤 다음 브랜드를 계속한다. 특정 브랜드 실행은 예외를 호출자에게 전파한다.

기존 중복 제거와 저장 정책을 그대로 사용한다. 전체 수집 성공 후 record의 **모든 필드가 같은 항목만** 제거하고 첫 순서를 유지한다. HTTP 동안 호출자 트랜잭션은 중단한다. 별도 Repository 프록시에서 브랜드 조건 DELETE와 배치 INSERT 전부를 한 트랜잭션으로 묶고, 커밋 후에만 성공을 기록한다. 실패한 브랜드의 이전 행·ID·수집 시각과 다른 브랜드 데이터는 보존한다.

## 스케줄과 하루 1회

`promotion.collection.enabled=false`를 유지하며 dev/prod 설정은 바꾸지 않는다. 자동 수집을 실행하지 않았다. 기존 스케줄은 KST 매일 04:00 한 번이며 즉시 재시도·기동 직후 실행은 없다.

Service는 동기화된 브랜드별 실행 상태와 마지막 시도 KST 날짜를 메모리에 저장한다. 동시에 같은 브랜드가 실행 중이거나 당일 이미 시도했다면 건너뛴다. 실패도 한 번의 시도이며 다음 KST 날짜에 다시 허용한다. 다른 브랜드는 독립적이다.

이 메모리 상태는 **한 JVM의 같은 Service Bean에서만 유효**하다. JVM 재시작·여러 앱 인스턴스·다른 컴퓨터의 명령 사이에는 공유되지 않는다. 로컬 수동 `--live` 명령은 사용자 홈 `.jachwi-sunbae/promotions/seven-eleven-YYYY-MM-DD.attempt` 파일을 CREATE_NEW로 생성해 같은 사용자 명령 간 당일 반복도 막는다. 파일 생성 실패도 외부 요청 전에 중단하며 실패 후 기록을 지우거나 당일 재시도하지 않는다. 이 파일은 앱 스케줄러와 공유하는 분산 잠금이 아니다.

실제 연동을 켤 때는 실행 주체를 하나로 한정하고 당일 수동 수집 여부를 확인해야 한다. 현재 실험의 기본값은 OFF이며 재시작·다중 인스턴스를 포함한 공유 실행 이력 보장은 후속 과제다. 분산 잠금·Redis·Quartz는 추가하지 않았다.

## 로컬 실행

Java 21·로컬 Docker가 필요하다. 아래 작업은 항상 새 `promotion_local` MySQL 컨테이너를 만들고 기존 저장 Service를 호출한다. DB URL·Spring 프로필·DB 환경변수로 대상을 변경할 수 없고 원격 Docker도 거부한다. 종료하면 DB는 삭제된다. 기존 로컬 앱 DB를 적재하는 명령이 아니다.

```bash
cd backend
./gradlew storeSevenElevenPromotionsLocally --args='--fixture' --no-daemon
```

fixture는 실제 세 탭의 첫 화면 39건과 중복 제거 검증용으로 한 번 더 넣은 동일 항목 1건이다. **원본 40 → 중복 1 → 저장 39**는 표본 검증이며 실제 전체 수집 결과가 아니다. 명령은 모드·출처·행사별 수·UNKNOWN 수·중복 수·저장 수·마지막 정상 저장 시각과 SQL 집계를 출력한다.

다음 명령은 당일 수집을 아직 시도하지 않았을 때에만 실행한다. 새 응답 폴더를 지정해야 한다. 2026-10-27은 이미 한 번 실패한 수집 이력이 있으므로 다시 실행하지 않았다.

```bash
./gradlew storeSevenElevenPromotionsLocally \
  --args='--live /tmp/seven-eleven-new-capture' --no-daemon
```

Client의 실제 응답을 `tab1-first.html`, `tab1-page2.html` 형태로 보관한다. 네 탭의 파싱과 전체 수집이 끝난 뒤에만 `completed.txt`를 기록하고 DB 저장으로 넘어간다. HTTP 200 외 상태(403·429·리다이렉트 포함)와 통신 실패는 재시도·우회 없이 중단한다. 부분 응답은 조사 자료로 남지만 정상 DB 목록으로 저장하지 않는다.

완료한 응답 폴더는 외부 요청 없이 여러 번 재생해 DB 저장을 검증할 수 있다.

```bash
./gradlew storeSevenElevenPromotionsLocally \
  --args='--replay /tmp/seven-eleven-completed-capture' --no-daemon
```

`completed.txt`가 없으면 Docker 시작 전에 거부한다. 완료 표시가 있더라도 실제 Fetcher·Parser를 거쳐 모든 파일·수량을 다시 검증한다. 재생 저장의 `collectedAt`은 Service가 이번 재생 저장 시점에 생성하는 KST 시각이며 과거 원격 수집 시각으로 가장하지 않는다.

## 조회 API

```http
GET /api/promotions?brand=SEVEN_ELEVEN
Authorization: Bearer <ACCESS_TOKEN>
```

기존 JWT·성공/오류 응답·저장 순서·`+09:00` 수집 시각·빈 목록 정책을 유지한다. JSON은 `brand`, `count`, `collectedAt`, `products`이며 상품에는 `name`, `price`, `imageUrl`, `category`, `promotionType`을 반환한다. 세븐일레븐 미분류는 `"category":"UNKNOWN"`이다. 조회 요청은 외부 수집·저장을 실행하지 않는다. 필터·검색·페이지네이션·전용 Controller는 추가하지 않는다.

## 실제 수집 결과와 검증 범위

2026-10-27 공식 첫 화면에서 표시한 총수는 다음과 같다.

| 행사 | 공식 화면 총수 | 확보한 범위                            |
| ---- | -------------- | -------------------------------------- |
| 1+1  | 919            | 첫 화면 13 + 추가 65페이지 650 = 663건 |
| 2+1  | 926            | 첫 화면 13건                           |
| 증정 | 0              | 첫 화면 및 빈 Ajax                     |
| 할인 | 484            | 첫 화면 13건                           |
| 합계 | 2,329          | 부분 표본 689건                        |

2,329는 **화면 총수의 합**이며 실제 전체 수집 완료 수·중복 제거 후 수가 아니다. 1+1 67페이지에서 15초 응답 시간 초과가 발생해 전체 수집을 실패로 종료했다. 당일 재시도하거나 다른 유형의 전체 수집을 별도로 실행하지 않았다. 조사 중 확인한 Ajax 1페이지의 반복 10건은 위 부분 표본에 다시 더하지 않았다.

## 2026-10-29 추가 검증

기존 수집의 Python 오류는 `opener.open(..., timeout=15)`에서 HTTP 상태줄을 읽던 SSL socket read 중 발생했다. HTML 파싱·DB 저장 전이며 403·429를 받은 기록은 없다. 1~66페이지 로그에는 응답 소요 시간이 없어 점차 느려졌는지는 **미측정**이다. 파일 수정 시각에서 응답 시간을 추정하지 않는다. 서버 처리 지연과 통신 구간 지연 중 어느 것이 원인인지는 확인하지 못했다.

Python은 urllib의 socket timeout 15초를 사용했고 Java는 RestClient/JDK의 연결 3초·읽기 15초를 별도 설정했다. 추가 페이지의 form 파라미터는 같고 Java는 첫 화면도 pTab POST로 읽는다. 클라이언트 구현이 다르므로 Python 실패가 Java에서도 동일하게 발생한다고 단정하지 않는다.

이번 검증에서 세븐일레븐 읽기 제한만 **30초**로 조정한다. 매일 한 번, 재시도 없이 수백 페이지를 순회하는 조건에서 단일 응답에 15초의 추가 여유를 허용하는 선택이다. 지연 원인을 해결했다거나 30초가 최적이라고 판단한 것은 아니다. 이마트24 설정, 연결 3초, 응답 이후 1초 간격, 200 외 상태·403·429·리다이렉트 중단 정책은 그대로다.

Client는 요청별 `tab`, `page`, 상태, `waitMillis`, `httpElapsedMillis`와 실패 유형을 기록한다. HTTP 시간은 요청 시작부터 본문 읽기까지이며, 요청 전 1초 대기·응답 파일 저장·HTML 파싱을 제외한다. 네트워크 왕복과 클라이언트 처리 시간이 포함되므로 서버 내부 처리 시간과 같다고 해석하지 않는다. Fetcher는 페이지별 상품 수·누적 수·공식 전체 수, 실패한 탭·페이지와 전체 소요 시간을 기록한다. 전체 HTML은 로그에 출력하지 않는다.

새 저장 명령을 만들지 않고 기존 `storeSevenElevenPromotionsLocally --live`와 `--replay`를 사용한다. 저장 후 같은 일회용 DB에 연결된 실제 QueryService·Controller를 standalone MockMvc로 호출해 API의 count·products 수와 DB 수를 대조한다. 이 수동 검증은 실제 JWT 필터를 포함하지 않으며 JWT·익명 로그인은 기존 API 통합 테스트로 별도 검증한다. 개발용 JSON 매퍼는 애플리케이션처럼 날짜를 `+09:00` 문자열로 출력한다.

### E. 판단

**일부 보완 후 진행 가능**으로 판단한다. 1+1·2+1의 실제 마지막 페이지, 15초를 넘는 응답의 수신, 부분 수집의 저장 차단은 확인했다. 그러나 할인 목록의 수량 규칙이 미확정이고 전체 실데이터의 중복 제거·MySQL 적재·API 반환을 검증하지 못했으므로 현재 상태의 정식 반영은 보류한다.

먼저 공식 총수 484와 48페이지까지 실제 응답 480의 관계 및 이후 페이지 규칙을 확인해야 한다. 전체 응답을 정상 확보한 뒤 기존 `--replay`로 DB·API 건수를 검증한다. 당일 재실행이나 자동 예약을 등록하지 않았으며, 이 문제를 해결하려고 수량 검증을 완화하거나 재시도를 추가하지 않는다.
