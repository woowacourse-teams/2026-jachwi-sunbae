# GTFS 노선망 적재

KTDB(국가교통DB) GTFS 파일을 읽어 생활권 탐색에 쓸 버스·지하철 노선망을 `gtfs_*` 테이블에 적재한다.
적재는 무겁고 자주 하지 않는 운영 작업이라 공개 API 없이 애플리케이션 기동 옵션으로만 실행한다.

## 1. 적재 대상

| GTFS 파일        | 사용하는 값                                   | 적재 테이블      |
|------------------|-----------------------------------------------|------------------|
| `routes.txt`     | `route_type`이 `0`, `1`, `3`인 노선           | `gtfs_routes`    |
| `trips.txt`      | 대상 노선의 운행편                            | 적재하지 않음    |
| `stop_times.txt` | 운행편별 정차 순서와 도착·출발 시각           | `gtfs_edges`     |
| `stops.txt`      | 대상 노선이 실제로 지나는 정류장              | `gtfs_stops`     |
| `transfers.txt`  | 양쪽 정류장이 모두 적재 대상인 환승           | `gtfs_transfers` |

- `route_type` `1`은 지하철·도시철도, `3`은 GTFS 표준 버스다. KTDB 데이터는 버스에 `0`도 사용한다. 일반철도(`2`) 등은 적재하지 않는다.
- 같은 노선에서 연속한 두 정류장을 하나의 구간으로 만들고, 운행편마다 다른 이동 시간의 중앙값을 대표 이동 시간으로 저장한다. 같은 분에 도착하는 구간도 최소 30초로 본다.
- 노선별 탑승 대기 시간(`wait_seconds`)은 첫 정류장 출발 시각 간격 중앙값의 절반이며 2분 이상 15분 이하로 제한한다. 1분 미만·2시간 초과 간격은 제외하고, 쓸 간격이 없으면 5분으로 둔다.
- 같은 정류장 쌍의 환승이 여러 번 나오면 가장 짧은 환승 시간을 남긴다.
- 파일 앞의 UTF-8 BOM과 24시를 넘는 막차 시각(예: `25:10:00`)을 처리한다.

## 2. 테이블 준비

로컬은 빈 MySQL 볼륨을 만들 때 [초기화 SQL](../../src/main/resources/db/init/001-schema.sql)이 `gtfs_*` 테이블을 함께 만든다.
이미 볼륨이 있다면 초기화 SQL이 다시 적용되지 않으므로 `001-schema.sql`의 `gtfs_*` `CREATE TABLE` 문만 실행한다.

dev·prod RDS는 애플리케이션이 스키마를 바꾸지 않는다. `gtfs_*` 테이블은 기존 데이터와 참조 관계가 없으므로 같은 `CREATE TABLE IF NOT EXISTS` 문을 배포 이슈에 기록한 뒤 수동으로 실행한다.

## 3. 적재 실행

GTFS 파일 다섯 개가 들어 있는 디렉터리를 지정하고 적재 옵션을 켠 채 애플리케이션을 실행한다.

```bash
GTFS_DIRECTORY=/path/to/gtfs GTFS_IMPORT_ON_STARTUP=true ./gradlew bootRun
```

- 적재는 기존 `gtfs_*` 데이터를 모두 지우고 새로 채운다. 파일을 다 읽은 뒤 삭제와 저장을 한 트랜잭션으로 실행하므로 실패하면 이전 데이터가 남는다.
- 적재가 끝나면 `gtfs_import_completed` 이벤트 로그에 노선·정류장·구간·환승 건수를 남긴다.
- 디렉터리가 없거나 파일을 읽지 못하면 애플리케이션 기동이 실패한다.
- 적재가 끝나면 `GTFS_IMPORT_ON_STARTUP`을 다시 `false`로 둔다. 켜 두면 재시작할 때마다 다시 적재한다.
