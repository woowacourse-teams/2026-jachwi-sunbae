# ADR-0013: 통합 스키마 변경 이력을 Flyway로 관리한다

- 상태: 승인
- 결정일: 2026-09-03
- 참여자: 자취선배 백엔드 팀
- 대체 대상: [ADR-0009](0009-use-disposable-database-schema.md), [ADR-0011](0011-apply-idempotent-database-upgrades.md), [ADR-0012](0012-deploy-mvp2-with-team-pipeline.md)의 DB 실행 경계

## 맥락

MVP2가 기능을 확장하면서 회원 인증 정보 병합, 매물 주소 통합, 매물 부가정보 분리, 옵션 코드화, 논리 삭제와 체크리스트 선호 저장을 한 번에 도입해야 한다. 기존 `DatabaseUpgradeInitializer`는 애플리케이션 시작마다 모든 SQL을 다시 실행하므로 적용 이력·체크섬·동시 기동 잠금을 제공하지 않는다. 이미 운영 이력이 있는 팀 RDS의 `flyway_schema_history`를 새 이력과 섞으면 과거 버전 파일 검증이 현재 코드와 충돌할 수 있다.

## 결정

- Spring Boot의 Flyway 자동 구성을 활성화하고 `classpath:db/migration`의 버전 SQL만 기본 프로필에서 실행한다.
- 새 이력 테이블은 `integrated_schema_history`로 분리한다. 기존 `flyway_schema_history`는 읽거나 수정하지 않고 보존한다.
- 이미 테이블이 있는 DB는 `baseline-on-migrate=true`, 기준선 버전 1로 등록한 뒤 V2 이후를 적용한다. 빈 DB는 V1부터 전체 버전을 적용한다.
- V1은 현재 MVP2 기준 스키마, V2는 기준 데이터, V3은 통합 구조 확장, V4는 데이터 backfill과 변환 실패 기록, V5는 주소 길이 보정을 담당한다.
- V3·V4에서는 레거시 컬럼과 `nickname_credentials`를 즉시 삭제하지 않는다. API 전환과 데이터 검증이 끝난 뒤 별도 순방향 버전에서 정리한다.
- `DatabaseUpgradeInitializer`는 호환 테스트에서만 명시적으로 활성화할 수 있고 운영 기본값은 비활성화한다.

## 근거

- Flyway가 버전, 적용 순서, 체크섬, 성공 여부와 단일 실행 잠금을 관리해 여러 인스턴스 배포에서 재실행을 방지한다.
- 기준선과 확장·backfill을 분리하면 기존 데이터가 있는 DB와 새 DB가 같은 최종 구조로 수렴한다.
- 별도 이력 테이블을 사용하면 과거 Flyway 이력을 훼손하지 않으면서 통합 스키마의 새 이력을 검증할 수 있다.
- nullable 확장과 논리 삭제를 먼저 적용하면 이전 애플리케이션을 순방향으로 롤백할 수 있고, 데이터 삭제 없이 API 전환을 단계적으로 진행할 수 있다.

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| 시작 시 멱등 SQL을 계속 실행 | 도입 비용이 낮음 | 적용 이력·체크섬·동시 실행 잠금이 없고 실패 지점을 추적하기 어려움 |
| 기존 `flyway_schema_history`를 재사용 | 테이블이 하나로 단순함 | 과거 V1~V11 스크립트와 현재 기준선의 checksum·누락 검증이 충돌함 |
| 기존 스키마를 폐기하고 새 DB로 시작 | 구현이 빠름 | 운영 회원·매물·메모를 보존해야 하는 통합 요구와 맞지 않음 |

## 결과와 트레이드오프

- 마이그레이션 파일은 적용 후 수정할 수 없고 새 버전 파일을 추가해야 한다.
- MySQL DDL의 암시적 커밋으로 실패 시 모든 변경이 자동 원자적으로 되돌아가지 않으므로 운영 전 논리 백업과 복원 리허설이 필요하다.
- V4는 해석할 수 없는 메모 값을 NULL로 보존하고 `migration_backfill_failures`에 기록한다. 실패 목록을 확인한 뒤 후속 보정 SQL을 추가한다.
- V5는 기존 주소 값을 보존한 채 `properties.address`를 `VARCHAR(500)`으로 넓힌다.
- `db/init/`과 `db/upgrade/`는 호환 테스트용 보관 경로로 남지만 기본 애플리케이션 실행 경로가 아니다.

## 검증 방법

- Testcontainers MySQL 8.4에서 V1~V5 적용 후 `integrated_schema_history`의 성공 버전과 pending 0건을 확인한다.
- 기존 테이블과 과거 `flyway_schema_history`가 있는 DB에서 기준선 등록 후 V2~V5만 적용되는지 확인한다.
- 회원 hash 보존, 주소 우선순위, 다섯 가지 부가정보, 옵션·공과금 alias, 자유 메모 보존과 변환 실패 목록을 검증한다.
- 애플리케이션 전체 테스트와 문서 정합성 검사를 통과시킨다.

## 재검토 조건

- 운영 DB가 여러 리전에 분산되거나 대규모 테이블 변경으로 온라인 스키마 변경 도구가 필요해지는 경우 실행 전략을 재검토한다.
- 모든 API가 통합 컬럼만 사용하고 레거시 데이터 검증이 끝나면 `nickname_credentials`, 도로명·지번 컬럼과 구조화 메모의 제거 시점을 별도 ADR로 결정한다.
